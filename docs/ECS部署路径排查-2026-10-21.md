## 结论

服务器确实留有两种发布入口，但检查时只有一个 Node 业务进程和一个 PM2 `cangshu` 应用在运行。没有发现两个服务同时抢占 80 端口，或后台任务自动反复切换版本的证据。

已证实的问题是部署路径、启动方式和数据路径不一致。不同部署流程复用同一个 PM2 应用名，可以把服务指向不同版本或不同数据库；这会表现为更新失效、旧界面重新出现或账号数据变化。仅保留旧 release 目录作为回滚备份，本身不会覆盖正在运行的版本。

## 配置歧义及触发条件

1. 仓库 `ecosystem.server.config.cjs:4` 的默认工作目录仍为 `/opt/cangshu`；`:19` 的静态路径跟随该目录；`:20` 的默认数据路径为 `${APP_DIR}/server/data`。
2. 之前的独立 release 发布通过显式环境变量指定 release 路径和 `/var/lib/cangshu`。本次按仓库默认配置发布，形成另一套代码和数据入口。这两个约定没有在仓库内统一。
3. 更新 `/opt/cangshu` 后只执行同名 PM2 应用的 restart/reload，不能凭目录更新成功就认定 PM2 已切换工作目录和脚本路径。必须核对实际进程路径、静态目录、数据目录和保存配置，否则可能产生版本未切换或前后端版本不一致。当前这些路径已一致。
4. `/opt/cangshu-releases/current` 仍指向旧的 `/opt/cangshu-releases/cangshu-20260929-settlement-64e3b8b0`，不是当前服务的入口。后续若将该链接当作当前版本直接启动，会启动旧版本。

检查了 PM2 runtime/dump、进程和监听端口、systemd 服务/定时器、cron/rc.local/shell 启动引用以及 Git hooks。没有发现另一套 cangshu 服务、相关定时发布任务或 Git 部署钩子；PM2 `watch=false`、无 `cron_restart`，应用错误日志中未发现 `EADDRINUSE`。现有证据支持“不同发布流程轮流重配同一个服务”的推断，不能据此认定存在两个自动运行的发布器。

## 建议的收口顺序

1. 固定唯一发布协议：Git 完整 SHA → 独立 release 构建 → 校验 → 单个 PM2 `cangshu` 切换。旧 release 只作为回滚材料；将 `current` 链接与实际运行版本对齐，或明确弃用它，不能继续保持歧义。
2. 数据固定在发布目录之外。沿用已有 `/var/lib/cangshu` 约定前，先对两份数据库做一致性备份并核对差异，保留当前 LLM 使用产生的新数据；不能直接把当前服务切回旧数据库。
3. 将默认 PM2 配置、唯一部署脚本和项目部署说明一起统一。切换必须同时校验 PM2 脚本、cwd、静态目录、固定数据目录、运行 Git SHA、健康接口，并在成功后保存 PM2 配置。
4. 当前有 2 个内存房间，正式切换应安排空房间窗口。统一数据来源之前，不删除任何旧数据库或 release。
