# 仓鼠聚会：唯一 ECS 发布流程

本说明取代仓库早期的 `git pull && pm2 restart`、上传ZIP、临时环境变量指定目录等步骤。所有Agent先读根目录 `AGENTS.md`。

## 固定布局

| 用途 | 唯一位置 |
|---|---|
| 应用入口 | `/opt/cangshu`，必须是符号链接 |
| 固定版本 | `/opt/cangshu-releases/<完整40位Git SHA>` |
| 正式数据库 | `/var/lib/cangshu/hamster.db` |
| 服务器模型Key、模型参数、建房码 | `/etc/cangshu/runtime.json`，0600，不进Git、不展示内容 |
| 进程 | PM2 `cangshu`，一个fork实例，80端口 |
| 开机恢复 | `pm2-root.service` + 统一流程保存的PM2配置 |
| 备份/历史归档 | `/var/backups/cangshu`，0700，不作为发布目录 |
| 发布锁 | `/var/lock/cangshu-deploy.lock` |

8080仍是独立万象棋Wiki，不修改它的服务、文件或安全组。

## 正常发布与回滚

1. 检查工作树，仅提交本任务内容；合入并推送 `feature/room-repo`。所有运行文件都应纳入Git。
2. 在本地项目执行 `npm run deploy:ecs -- <完整SHA>`。使用已有Workbench登录；不粘贴服务器凭证，不手工启动PM2。
3. 脚本在服务器独占加锁，从Git检出固定SHA，安装并构建客户端。校验目标包含LLM基线、工作区干净、无房间后才切换。
4. 切换时删除原PM2进程定义、原子替换唯一入口链接，再按固定配置启动，避免reload保留旧脚本路径。验证脚本/cwd、静态目录、数据库路径、Git SHA、首页/资源/健康接口和Wiki后保存PM2配置。失败自动恢复并验证前一版本。
5. 本地执行 `npm run deploy:ecs -- --status`，另从公网检查 `http://8.133.3.206/`。这是80端口HTTP，无TLS。

回滚同样执行步骤2，SHA指定此前以统一流程发布的版本。数据库不会跟随代码回滚，不从旧归档恢复数据库；有不兼容数据库迁移时先另行设计恢复步骤。

发布中另一个Agent会得到“已有发布操作正在运行”，应等待现有发布结束再读状态。不得用新PM2应用名或其他路径绕过锁。若提示有房间，等房间结束并退出；不得强制重启。

## 首次迁移（仅此次用户已授权账号清空）

执行 `npm run deploy:ecs -- <包含统一发布工具的完整SHA> --bootstrap-reset`。

该操作仅接受尚未统一的 `/opt/cangshu` 实目录；再次执行会拒绝。进行中的牌局仍会阻止切换，已结束或等待中的房间会随账号重置结束。

脚本先构建候选代码，从现有PM2内部保存模型和建房参数到私有配置文件；停止旧服务后，用SQLite备份API备份两份数据库（包含WAL中的有效数据），再保留旧数据库文件及整个旧检出目录于备份目录。正式数据库重新初始化，账号、个人模型Key、账本和历史清空；服务器级模型参数和Key保留。旧release和过期current链接随后归档，生产路径只保留新的统一入口。

账号清空后用户需要重新注册，并重新填写个人模型Key。全局Key不会显示在任何诊断输出中。

## 排查规范

- 状态命令的 `release`、`current` 必须相同；SHA为完整Git版本；数据目录必须是 `/var/lib/cangshu`。
- `runtime.json` 必须只包含允许的模型/建房设置，不能覆盖代码、静态目录、数据库或监听端口。配置错误仅报告字段名，不能打印文件内容。
- 不使用 `cat pm2 dump`、`pm2 env`、完整 `/proc/*/environ`、shell历史等会展示凭证的诊断方式；只输出必要路径、状态和Key是否配置的布尔值。
- 不删除备份。若自动回滚失败，保留现场，用报告中的前一版本和私有备份恢复；不得循环重启或从旧数据目录试错。
- `docs/ECS部署路径排查-2026-10-21.md` 是迁移前检查快照，描述的旧目录不再是有效发布入口。
